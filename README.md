# MineOS — Simulator of Scheduling and Memory Management in Minecraft

**A simulation of operating system concepts applied to Minecraft server performance.**

A Minecraft (Java) server behaves like a miniature operating system:

- **Clock:** A 50 ms game loop (the _tick_).
- **Processes:** Thousands of tasks generated by players, mobs, entities, and redstone.
- **RAM:** Loaded chunks stored in memory.
- **Disk:** Persistent storage used when chunks must be loaded.

MineOS applies operating system concepts from scheduling, virtual memory, and I/O management to understand why Minecraft servers experience lag and which architectural decisions can improve performance.

---

## Project Overview

The project consists of two interconnected components:

1. **A real Paper server plugin** that records server activity and exports execution traces.
2. **A simulator** that replays those traces and compares different scheduling, memory management, and I/O policies.

# 1\. System Model

## 1.1. Tick Loop

The simulation follows Minecraft's 20 TPS model, where each tick has a target duration of 50 ms.

Tick $k$ begins at:

text

```text
max(end of previous tick, k * 50 ms)
```

If the workload requires more than 50 ms, the tick is extended.

This produces:

- **MSPT:** Milliseconds per tick.
- **TPS:** Ticks per second.

When MSPT exceeds 50 ms, the server cannot maintain 20 TPS, resulting in performance degradation.

## 1.2. Tasks and Priorities

Each task has an associated CPU cost and requires a chunk to be present in RAM.

The simulator defines four task types with static priorities:

| Task Type | Priority | Description |
| --- | --- | --- |
| `PLAYER` | 0 | Player-related operations |
| `REDSTONE` | 1 | Redstone processing |
| `ENTITY` | 2 | Entity and mob updates |
| `CHUNK_TICK` | 3 | Chunk-related updates |

Lower priority numbers represent more important tasks.

## 1.3. Memory Management

Each Minecraft chunk is modeled as a memory page, while RAM consists of page frames.

When a task accesses a chunk that is not currently in RAM, a **page fault** occurs.

The simulator then:

1. Selects a victim page using FIFO, LRU, or Clock.
2. Loads the required data from disk.
3. Takes approximately 1.5 ms for the disk operation.
4. Resumes the blocked task when the data becomes available.

The simulator supports two I/O approaches:

- **Synchronous I/O:** The main thread waits for the disk operation, reproducing the behavior of the vanilla architecture.
- **Asynchronous I/O:** The task is blocked while the CPU continues executing other available tasks. I/O is handled by 1–2 dedicated threads.

## 1.4. Policy Comparison

The simulator compares three major dimensions:

| Dimension | Available Options |
| --- | --- |
| **CPU Scheduling** | FCFS (vanilla), PRIORITY (4 levels + Round Robin + aging), MFQ (3 levels with degradation and boosting) |
| **Chunk Replacement** | FIFO, LRU, CLOCK |
| **Architecture** | Vanilla (synchronous I/O), Async, Budget, Prefetch-Naive, Prefetch-Throttled |

### Tick Budget

The budget architecture limits the amount of work performed during each tick to 50 ms.

When the budget is exhausted:

- Remaining tasks are deferred to the next tick.
- New updates for an entity can be discarded if that entity already has a pending update.
- Less critical elements receive fewer updates.

This approach maintains a target of 20 TPS at the cost of reduced update frequency.

### Performance Metrics

The simulator measures:

- Mean, p95, and p99 MSPT.
- TPS.
- Percentage of ticks exceeding 50 ms.
- CPU utilization.
- Disk utilization.
- Number of page faults.
- Memory hit ratio.
- Task latency (creation → completion), by task type.
- Percentage of discarded updates.

# 3\. Experimental Findings

See `docs/` and `results/results.csv` for the complete results.

### Experimental Setup

- One random seed per scenario.
- 100 warm-up ticks.
- 1,100 measured ticks after warm-up.
- Identical workload traces for policy comparisons.

Large performance differences are robust. Small differences (such as the approximately 1% difference between LRU and Clock) fall within the range of noise and should not be overinterpreted.

## 3.1. Priority Scheduling Protects Players

Priority scheduling significantly reduces player latency compared with FCFS.

| Scenario | Priority p99 | FCFS p99 |
| --- | --- | --- |
| Medium | 5.1 ms | 48 ms |
| Heavy | 7.3 ms | 110–123 ms |

However, this improvement comes at the expense of low-priority tasks.

Under Priority scheduling, `CHUNK_TICK` reaches a p99 latency of 271 ms and loses 47% of its updates.

**Conclusion:** Priority scheduling protects critical player operations but can severely degrade background tasks.

## 3.2. MFQ Does Not Understand Task Importance

Multi-Level Feedback Queue (MFQ) scheduling prioritizes short tasks rather than tasks that are important to gameplay.

Since most tick-related operations consist of small tasks, they end up competing with other operations in the same queues.

In the medium scenario:

| Scheduler | Tick-related p50 latency |
| --- | --- |
| PRIORITY | 2.6 ms |
| MFQ | 19 ms |

Under heavy workloads, MFQ can also cause severe starvation.

With a budget applied to the heavy scenario, Redstone processing reaches a p99 latency of approximately 7 seconds, even with performance boosting.

**Conclusion:** A scheduler should consider task importance, not only task execution history or duration.

## 3.3. Tick Budget Prevents Total System Collapse

Budgeting transforms an overloaded server into a system with controlled degradation.

| Configuration | TPS | Entity Updates |
| --- | --- | --- |
| Heavy without budget | 9 TPS | Normal processing |
| Heavy with budget | 20 TPS | 56–66% discarded |

The budget maintains 20 TPS by limiting work per tick, but this comes at the cost of significantly fewer entity updates.

**Conclusion:** Maintaining stable TPS does not necessarily mean maintaining the same gameplay simulation quality.

## 3.4. Asynchronous I/O Significantly Improves Performance

Synchronous I/O is one of the most expensive operations in the vanilla architecture.

In the medium scenario with 1,500 frames:

| Architecture | MSPT | TPS |
| --- | --- | --- |
| Vanilla (synchronous I/O) | 70 ms | 14.3 |
| Async I/O | 46.8 ms | 20 |

Asynchronous I/O allows the CPU to execute other tasks while disk operations are pending.

**Conclusion:** Separating I/O operations from CPU execution can significantly improve server responsiveness.

## 3.5. LRU and Clock Outperform FIFO

The memory replacement algorithms produce significantly different page fault rates.

**General performance:**

text

```text
LRU ≈ CLOCK << FIFO
```

FIFO produces between 42% and 100% more page faults, depending on the scenario.

| Scenario | FIFO Increase |
| --- | --- |
| Light | +42% |
| Medium | +62% (27,501 vs. 16,977) |
| Explorers | +69% (10,986 vs. 6,493) |
| Heavy | +100% |

Clock achieves results comparable to LRU while requiring only one reference bit per frame.

**Conclusion:** Clock provides an attractive balance between performance and implementation simplicity.

## 3.6. Thrashing Creates a Performance Cliff

Memory pressure does not necessarily cause gradual performance degradation.

In the medium scenario using LRU:

| Available RAM | TPS | Disk Utilization |
| --- | --- | --- |
| 100% | 20 | 23% |
| 80% | 19.9 | 93% |
| 60% | 11.7 | — |
| 40% | 4.7 | — |

At 80% RAM, the server still maintains approximately 20 TPS, but disk utilization jumps to 93%.

Further reductions in available RAM cause severe performance degradation.

**Conclusion:** Thrashing behaves like a performance cliff. Once memory pressure becomes sufficiently high, disk activity can overwhelm the system.

## 3.7. Naive Prefetching Can Make Performance Worse

Naive prefetching attempts to load chunks before they are needed.

However, unnecessary disk operations can saturate the disk and delay essential reads.

In the explorers scenario:

| Metric | No Prefetching | Naive Prefetching |
| --- | --- | --- |
| p99 tick time | 18 ms | 33 ms |
| Useful reads | 5,077 | — |
| Wasted reads | — | 4,704 |

Throttled prefetching produces significantly better results.

It only preloads data when the disk is idle.

Results:

- Page faults decrease by 36% (6,493 → 4,181).
- Tick duration remains approximately 18.4 ms.
- Nearly all preloaded data is utilized (2,325 useful / 65 unused).

**Conclusion:** Prefetching is beneficial only when it does not interfere with essential I/O operations.

## 3.8. CPU Scheduling Can Negatively Affect Disk Performance

An effective CPU scheduler does not necessarily guarantee better overall system performance.

Under memory pressure, Priority scheduling can defer tasks with the highest page fault rates.

As a result, their disk read requests are issued only when the CPU has no other pending tasks.

Although the number of page faults remains unchanged, the additional waiting time increases tick duration.

Example comparison under a light load:

| Scheduler | Tick Duration |
| --- | --- |
| PRIORITY | 31.5 ms |
| MFQ | 19.4 ms |

**Conclusion:** Real operating systems must consider the relationship between CPU scheduling and I/O scheduling. I/O-bound processes may require special treatment to prevent unnecessary delays.

# 4\. Limitations

The following limitations are relevant when interpreting the experimental results.

## 4.1. Synthetic CPU Costs

CPU costs are generated using fixed distributions rather than empirically measured values.

The qualitative conclusions (which approach performs best, why, and where performance degrades) are useful, but absolute figures do not represent a specific real-world server.

Real server traces would be required to replace these synthetic costs.

## 4.2. Random Seeds

Only one random seed is used per scenario.

Consequently, no confidence intervals or statistical significance tests are provided.

## 4.3. CPU Architecture

The simulation uses a single CPU thread.

Parallel execution across regions, as implemented by Folia, is not modeled.

## 4.4. Entity and Chunk Behavior

Entities and Redstone components are static; only players move.

Writing dirty chunks to disk during eviction is also not modeled.

## 4.5. I/O Latency

I/O latency is assumed to be constant.

The model does not account for differences between SSDs and HDDs or operating system caching.

## 4.6. Missing Server Operations

Real Minecraft server tick duration also includes operations that are not represented in this simulation:

- Network processing.
- Plugin execution.
- Garbage collection (GC).

These factors can influence real-world server performance.

## 6.3. Available Commands

| Command | Function |
| --- | --- |
| `/mineos record [ticks]` | Records players and mobs near a player into `plugins/MineOS/trace-*.csv`. |
| `/mineos status` | Displays average, p95, and p99 MSPT, along with the percentage of ticks exceeding 50 ms over the last 20 seconds. |
| `/mineos policy tiered` | Enables the tiered entity update policy. |
| `/mineos policy off` | Disables the tiered policy. |

### Tiered Policy

The tiered policy adjusts mob AI frequency according to distance from the player.

It uses three update frequencies:

- 1× normal frequency.
- 1/2 normal frequency.
- 1/4 normal frequency.

This reduces unnecessary entity processing for mobs farther away from players.

## 6.4. Validation Procedure

To compare the default behavior against the tiered policy, use the same server and workload.

**Step 1 — Disable the policy**


**Step 2 — Wait 20 seconds**

Allow the server to stabilize and collect measurements.

**Step 3 — Check server performance**

text

```text
/mineos status
```

Record the reported MSPT values.

**Step 4 — Enable the tiered policy**

text

```text
/mineos policy tiered
```

**Step 5 — Wait another 20 seconds**

Allow the new configuration to stabilize.

**Step 6 — Measure again**

text

```text
/mineos status
```

Compare the results from both configurations, especially:

- Average MSPT.
- p95 MSPT.
- p99 MSPT.
- Percentage of ticks exceeding 50 ms.

## 6.5. Plugin Limitations

There are important differences between the simulator and the real Paper server.

**CPU cost estimation**

Bukkit does not expose the CPU cost of individual entities.

Therefore, the recorded CPU cost is an _a priori_ model, scaled so that the modeled average tick time matches the measured server tick time.

This calibrates the total modeled cost, not the individual task cost distribution.

**Missing events**

The plugin does not record:

- `REDSTONE` events.
- `CHUNK_TICK` events.

**Mob AI control**

The tiered policy relies on:

java

```java
Mob#setAware
```

Its availability and actual behavior should be verified against the specific Paper version being used.

# 7\. Conclusion

MineOS demonstrates how operating system concepts can help explain and improve Minecraft server performance.

The experiments highlight several important principles:

1. **Priority scheduling** protects critical player operations but can starve background tasks.
2. **Asynchronous I/O** reduces CPU blocking and improves tick performance.
3. **LRU and Clock** provide better memory replacement behavior than FIFO.
4. **Tick budgeting** prevents total system collapse but sacrifices update frequency.
5. **Controlled prefetching** can reduce page faults without overwhelming disk operations.
6. **Memory pressure** can produce sudden performance degradation through thrashing.
7. **CPU and I/O scheduling** must be considered together to achieve balanced performance.

Ultimately, Minecraft server performance is not just a matter of CPU speed or available RAM. It is also a problem of scheduling, memory management, and I/O coordination.

**MineOS provides an experimental environment for studying these interactions and evaluating potential solutions.**
